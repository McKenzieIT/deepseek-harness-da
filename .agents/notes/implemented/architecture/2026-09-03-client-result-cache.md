# Agent Note: client result-cache — the object-layer hot cache over `result.get`

Status: implemented

## Problem

The INTERPRETATION renderers (`ui-present-table`, `ui-present-decomposition`) resolve a `present_table`/`present_decomposition` `result_id` to its rows. Without a client object-layer cache, every fold/expand re-render re-RPCs the host, and the v1 same-turn TSV scan (T4's `parseQueryData`) fails for any cross-turn reference or once event-window compaction drops the carrying message. [R5](../../../../wayfinder/interpretation-client-rendering/tickets/R5-object-layer-result-cache.md) decided the cache design (single package, byte-bounded LRU, event-driven invalidation, Config bounds, gen-token v1 skipped); [T8](2026-09-03-result-get-rpc.md) shipped the `result.get` miss path. This note records the implementation decisions beyond R5's resolution.

## Decision

A Mode 3 package `packages/client/result-cache/` provides `ctx.results` — a scope-addressed Cordis `Service` (name `results`) wrapping a byte-bounded `lru-cache` over the `IApiClient.results.get` seam (T8). `get(rid)` derives the caller's session via `sessions.scopeOf(this.ctx)` (the tracker rebinds `this.ctx` to the scoped ctx) and keys the LRU by `(sessionId, rid)`, so one session's rows never leak to another under a shared `qr_` id. A hit returns the same cached reference (no clone); a miss calls `result.get`, caches the entry if it fits the per-entry budget, and returns it; `result-not-found` resolves to `undefined` (not cached); any other failure rejects with a `ResultFetchError`. `connection/reset` flushes the whole cache (the runtime's sanctioned "wire-derived caches must treat their state as stale" signal).

- **Scope-addressed Service, not a per-session service instance.** R5's "session-scoped `ctx.results`, mirroring the host `ctx.resultCache` placement" is realized as one root `Service` whose `this.ctx` the Cordis Service tracker rebinds to the caller's scoped ctx — the `ConversationController` scope-addressing pattern — with `sessions.scopeOf` deriving the session and the LRU keyed by `(sessionId, rid)`. A true per-session service instance would require a hook into session-scope creation that no external package owns (the runtime mints scopes via `createScope` and owns the event stream); R5 ruled out runtime modification ("不内联进 runtime"). The scope-addressed form achieves the same cross-session isolation without runtime modification.
- **Byte-bounded LRU with explicit `maxEntrySize` admission.** `lru-cache` (isaacs) in `dependencies`, configured with `maxSize`/`sizeCalculation`/`maxEntrySize`/`max`/`updateAgeOnGet`. `sizeCalculation` is the JSON-serialized UTF-16 code-unit length of the entry — a proxy for retained memory, chosen so admission and eviction reason about the same shape that sits on the heap. An entry larger than `maxEntrySize` is fetched on demand and never cached (the admission decision is explicit in `get`, not just relied on from lru-cache's own guard — explicit-over-implicit at the boundary).
- **Bounds are named overridable constants, not `cordis.yml` Config.** R5's "Config fields from `cordis.yml`" is realized as `DEFAULT_RESULT_CACHE_CONFIG` (`maxEntrySize` ~8MB / `maxSize` ~64MB / `max` ~64 / `updateAgeOnGet true`) — named, documented, overridable at the `apply` construction site. Client packages receive construction config through the `ctx.plugin(Class, config)` idiom (the `ConversationController` precedent), not a schemastery `cordis.yml` Config; no client package in the tree uses a `dsh.client.config` field. Wiring the bounds to `cordis.yml` is deferred until that mechanism is established for client packages.
- **No per-`query_data` event subscription; invalidation is an API realized at the consumer boundary.** The cache exposes `invalidate(rid)`/`invalidateSession(sid)`/`invalidateAll()`. The fresh-`query_data` invalidation call lives in the consumer's inject face: `ui-present-table`/`ui-present-decomposition` already observe `query_data` tool-result nodes through the toolview slot props, so the natural home for `invalidate(rid)` is the consumer reacting to a fresh same-turn `query_data` for the id it is about to render. A cache-internal subscription has no sanctioned external tap (the `Session` object layer owns the conversation event stream; `ctx.conversationEvents` is a Conversation-Node Definition registry, not a raw event stream), and runtime modification / a Conversation-Node-as-pure-invalidation-side-channel were both ruled out. The `connection/reset` reconnect flush is wired here; the consumer wiring is T9 step 6 (graduated as a follow-up).
- **The wire `ResultEntry` is defined locally, not imported.** `src/client/types.ts` declares its own `ResultEntry`/`ResultMetadata` mirroring the apiproxy contract type, so this browser package stays self-contained at the type boundary — the same stance the apiproxy contract layer takes for its own `ResultEntry` (defined locally rather than imported from the host `dsh-result-cache` package). Structural identity makes the `api.results.get` result assignable without a cast.

## Alternatives considered

### Why not a per-session Cordis service instance (R5's literal "session-scoped `ctx.results`")?

Session-scoped services are provided on the per-session scoped `AgentContext` minted by the runtime's `createScope`. External packages cannot hook scope creation (it is runtime-owned), and `SessionProvideChannel` provides session-standard-*props* (hooks/props), not arbitrary services. A true per-session `ctx.results` would therefore require runtime modification, which R5 explicitly ruled out to avoid colliding with the runtime `index.ts`/`apply()` hot public surface. The scope-addressed `Service` (one root instance, tracker-rebound `this.ctx`, `scopeOf` derivation, composite key) achieves the same cross-session isolation and mirrors the `ConversationController` precedent exactly.

### Why not an explicit `get(sessionId, rid)` signature (sid as a parameter)?

R5's inject face is `inject: (sessionId) => ({ fetchResult: (rid) => ctx.results.get(rid) })` — `get` takes only `rid`, deriving the session implicitly. The scope-addressed form honors that: the consumer addresses the service through `sessions.scope(sessionId).get('results')`, so `scopeOf(this.ctx)` resolves the session. It also mirrors the host `ResultCache.get(resultId)` (the host ctx IS the session's) and `ConversationController.send(text)` (scope-addressed, no sid parameter). An explicit-sid signature would deviate from R5's inject-face contract + the host/conversation precedents.

### Why not a cache-internal subscription to `query_data` completion for invalidation?

The conversation event stream is owned by the runtime `Session`/`SessionManager` (`handleMuxEnvelope` → `acceptLiveEvent` → `conversation.append`); no cordis event is emitted on tool-result completion, and `ctx.conversationEvents` (`ConversationEventRegistry`) is a Conversation-Node Definition registry (for building view nodes), not a raw `subscribe(callback)` event stream. An external package cannot observe `query_data` completion without runtime modification (ruled out) or registering a Conversation Node Definition purely as an invalidation side-channel (a misuse of the view-node system; the `Conversation Node discipline` in `packages/client/AGENTS.md` discourages ad-hoc event switches). The consumer already sees `query_data` nodes through the toolview slot props, so the invalidation call belongs there. The `connection/reset` reconnect flush (sanctioned) covers the missed-event-during-reconnect case.

### Why not import `ResultEntry` from `@deepseek-ai/dsh-host-apiproxy/api`?

It is browser-safe and re-exported, but defining the wire shape locally keeps this package self-contained at the type boundary and avoids a direct dependency edge to the host apiproxy package — the same stance T8's note records for the apiproxy contract layer's own `ResultEntry`. Structural identity makes the RPC result assignable without a cast.

### Why not `structuredClone` on cache hit / IndexedDB spill / WeakRef eviction / TTL?

R5 + the 2026-H2 research ruled all four out. Hits return the same cached reference (results are immutable read-only views) — `structuredClone` is costly on large arrays and unnecessary. IndexedDB spill is for recoverable cross-session caches; this cache is session-scoped over an authoritative host (re-RPC is the recovery). `WeakRef`/`FinalizationRegistry` provide no capacity control and GC timing is not guaranteed. No TTL: `cr_` results are immutable-once-written and `qr_` results carry a point-in-time snapshot, so a TTL would evict hot entries prematurely; correctness is the invalidation API's job, not a timer's.

## Consequences

The client object-layer result cache is shipped and self-verifying: 21 tests anchor the byte-bounded LRU semantics (miss→fetch→cache hit with no clone and no second fetch, session-key isolation, `maxEntrySize` admission, `maxSize` byte eviction, the `max` count backstop, `updateAgeOnGet` recency, the `result-not-found`/error paths, and the `invalidate`/`invalidateScope`/`invalidateAll` API) and the scope-addressed `ctx.results` (session isolation, miss→`result.get`→cache, not-found/error, scoped invalidation, fail-loud from root scope). The T8 miss path is exercised end-to-end through a mock `IApiClient`.

**Supersession check:** no existing Agent Note owns the client result-cache seam. [T8's note](2026-09-03-result-get-rpc.md) owns the *host* `result.get` RPC (the seam this cache consumes), not the client cache; the [GUI web-client architecture](2026-07-19-gui-web-client-architecture.md) note owns the object-layer/render/presentation split, not this service. This note is the canonical record for `ctx.results`.

**Deferred (graduated as follow-ups):**
- *Consumer wiring* (T9 step 6): `ui-present-table`/`ui-present-decomposition` register the `fetchResult`/`invalidateResult` inject face and call `fetchResult(args.result_id)` instead of T4's TSV scan (which stays as a cache-miss fallback). Deferred because the wayfinder session's commit pathspec scopes this work to `packages/client/result-cache/`; the consumer is a stable, separately-committed package.
- *Per-`query_data` invalidation call site*: lives in the consumer (see above); the cache `invalidate(rid)` API is ready.
- *Generation token v1* (R5 Known Limitation): a missed `query_data` event may briefly serve stale rows until LRU eviction or the consumer's invalidation lands; the `qr_R#genN` key-rotation hardening is deferred (local to the cache, no API break) per R5.
- *`cordis.yml` Config wiring* for the four bounds: deferred until a client-package config mechanism is established.

**T8 residual surfaced (not fixed here):** building this package's `tsc -b` revealed that `packages/client/connection/src/client/fixture.ts` — the `FixtureApiClient`'s `ApiProxy` fake — was not updated when T8 added the `results` domain to `ApiProxy`/`IApiClient` (TS2741: `Property 'results' is missing`, plus a related missing-return). `tsc -b packages/client/connection/tsconfig.client.json` exits 1 independently of this package; the client tsc aggregate has been red since T8 (T8 verified `tsc -b apiproxy` + `tsc -b tsconfig.host.json` + `pnpm run test:gui`, none of which typecheck `connection/fixture.ts`). This package's own `src/` is tsc-clean (zero errors in `packages/client/result-cache/src`); `pnpm run test:gui` is unaffected (vitest transpiles via esbuild and does not typecheck `fixture.ts`). Per `packages/client/AGENTS.md` ("red on code you did not touch — neither silently fix nor ignore it: note it in your handoff"), the fixture residual is noted here rather than fixed in this session's pathspec-limited commit; it is a one-line mechanical T8 follow-up (add a `results` stub to the fixture's `ApiProxy` fake) that should land in a connection-scoped change.
