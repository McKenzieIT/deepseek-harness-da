# Agent Note: data-agent additive scaffold over dsh-base

Status: implemented

English | [中文](2026-08-19-data-agent-additive-scaffold.zh.md)

## Problem

`deepseek-harness-da` is a fork of `deepseek-ai/deepseek-harness` being repurposed into a data agent (natural-language to SQL and data retrieval). The data-agent capability plugins — query, retrieval and vectorization, semantic layer, audit, admin, plus the phase-1 `llm-dashscope` and `subagent-qoder` — are not yet built; they ship in later tickets. The effort still needs a place for them to mount and a way to declare the data-agent surface (its disabled code-agent tool set, its Code Mode off, its persona-less prompt base) without touching the shared `dsh-base` patch, the `dsh-app-boot` profile templates, or any shipped plugin source, so the fork keeps a clean upstream upgrade path. Two questions had to be settled before any data package ships: where data capability packages live and resolve, and how a data-agent profile composes its surface additively over `dsh-base`.

## Decision

A new patch-only bundle `@deepseek-ai/dsh-data-agent` rides directly over `dsh-base`, mirroring `dsh-base`'s package shape: a `cordis.patch.yml` declared by the `dsh.bundle.patch` manifest field, a no-runtime-API `src/index.ts`, and a noop `src/invariant.ts` companion. The bundle/profile composition it extends is owned by the [profile plugin bundles](2026-08-05-profile-plugin-bundles.md) decision. Its patch is **disable-only** for the code-agent surface and **commented placeholders** for the data plugins, so the bundle is installable and loadable today even though no data package exists yet.

`cordis.patch.yml` disables three base rows by id: `tool-str-replace-editor` and `tool-ralph` (both `disabled: true`), and the `tools` row's `mode: native` (Code Mode off) — the coding-agent tools a data agent does not use. Disabling rather than deleting holds regardless of a later `dsh-base` row reorder, the same discipline `dsh-web-app` applies when moving tools behind presets. `tool-pwsh` is not restated: `dsh-base`'s own `disabled: !!js process.platform !== 'win32'` already gates it off on POSIX. `tool-bash` and `code-runtime` are deliberately **not** disabled here — they are execution backends the data agent itself uses (shell, and pandas transforms), and the business-user tool-gate that keeps them away from end users is an intranet-exposure concern owned by a later ticket, not this profile layer. The data-plugin rows are a commented `- insert:` block naming each planned plugin, its ctx-key, and the ticket that ships it; an active `name:` specifier to a not-yet-shipped package would break `pnpm install` and `verify-cordis-config`, so each row stays inert until its package lands. The data-agent persona is not set here — it belongs to the four-phase preset that composes per session.

A new `packages/data/` group holds the data capability packages as they ship. Group registration is the additive edit the `tsconfig.base.json` source-path map requires for a new group: `./packages/data/*/src` joins the `@deepseek-ai/dsh-*` wildcard and `./packages/data/*/src/invariant.ts` joins the `@deepseek-ai/dsh-*/invariant` wildcard (the generic wildcards that map a package name to its source; an existing-group package needs no edit, a new group does). The new bundle joins `tsconfig.host.json`'s explicit `references`, since TS project references have no wildcard form. `packages/README.md` and `packages/bundle/README.md` gain the `data/` and `data-agent/` rows their tables require, and `packages/data/README.md` lists the planned packages with TBD names and ctx keys, each marked for its owning ticket. No `dsh-app-boot` profile template is added: `dsh --profile data-agent` is created out-of-tree through `dsh plugin --profile data-agent add @deepseek-ai/dsh-data-agent` once the four-phase preset and its driver land, so no shared boot glue is touched. The bundle's own `package.json` declares no `dependencies` (the patch mounts nothing yet), only the `cordis` and `dsh-invariants` peers its invariant companion imports.

## Verification

`pnpm install` reconciles the new workspace package with no dependency errors — the commented-row discipline introduces no bare specifiers. `dsh --profile headless --patch ./packages/bundle/data-agent/cordis.patch.yml --dump-config` composes the layer over `dsh-base` and `dsh-headless` and exits 0 with no absent-id warnings; the dump shows `tool-ralph` and `tool-str-replace-editor` at `disabled: true` and the `tools` row at `mode: native`, the literal overriding `dsh-headless`'s `!!js process.env.DSH_TOOLS_MODE` seam when composed via `--patch`. A narrow `tsc --noEmit -p packages/bundle/data-agent/tsconfig.json` type-checks the package against its `vendor/cordis` and `runtime-diagnostics/invariants` references. The pre-commit `verify-translation-pairing` gate passes for both bilingual READMEs, and `gen-module-graph` refreshed `docs/module-graph.md` for the new package.

## Alternatives considered

- **A runnable one-shot bundle mirroring `dsh-headless` (startup provider and runner).** The four-phase preset that drives the data agent is unbuilt, so a runner would fix a runtime contract (`appExit`, agent creation, task positional) the preset later reshapes — premature and bound for rewrite. Runnability is composition with a driver, not a `dsh-data-agent`-owned runner.
- **A `data-agent` profile template in `dsh-app-boot` (`PROFILE_TEMPLATES`).** Only `web` and `headless` ship as templates, and a `data-agent` template over a patch-only bundle with no driver would boot to idle. Adding it edits shared boot glue and conflicts on upstream merge; the out-of-tree `dsh plugin --profile data-agent add` path creates the profile without touching the installation.
- **Active `- insert:` rows for the data plugins plus stub packages now.** A bare specifier to a not-yet-shipped package breaks `pnpm install` and `verify-cordis-config`, and stub packages would fix contracts the later tickets own. Commented placeholders give each owning ticket its mount point without a load-time lie.
- **Disabling `tool-bash` and `code-runtime` in this bundle.** The data agent uses them as execution backends (shell; pandas transforms, including report and Excel generation); gating them from business users is an intranet-exposure tool-gate owned by a later ticket, not this profile layer. A bundle-level disable removes the agent's own tools at the wrong layer.
- **Setting the data-agent persona in the bundle.** The four-phase preset owns persona per session; a bundle placeholder would be rewritten by the preset and steps on its ownership.
- **A per-package tsconfig wildcard instead of a group wildcard.** Unnecessary: the generic `./packages/data/*/src` wildcard maps every package under the new group once added; only the group itself needs the additive wildcard entry, and TS project references in `tsconfig.host.json` stay explicit per package.

## Consequences

- The data-agent surface (code-agent disabled, Code Mode off, persona deferred) is established additively over `dsh-base` with zero edits to base, core, app-boot, plugin source, or profile templates — the fork's upstream upgrade path stays clean.
- Later data-capability tickets mount by uncommenting their reserved row and supplying the package `name:`; the group wildcard already resolves their source, and the bundle already sits in the host aggregate's `references`.
- The bundle is loadable today and composes correctly with a driver (`--patch` over `headless`), so the scaffold is observable before any data plugin ships.
- `tool-bash` and `code-runtime` stay enabled at the bundle layer; their exposure to business users is a separate, later intranet tool-gate decision. `code-runtime` is not even mounted yet (base does not insert it) — it mounts when the four-phase transform stage lands.
- Report and Excel artifact delivery surfaced as a separate design item: text reports flow through `tool-fs` `write` (a mutation tool, kept), but binary artifacts (Excel, PDF) cannot use `tool-fs` or `tool-str-replace-editor` (both are UTF-8 text only) and need `code-runtime` (pandas) plus a deliverable mechanism (`ctx.attachments` reuse or a dedicated export tool) owned by a later ticket.
