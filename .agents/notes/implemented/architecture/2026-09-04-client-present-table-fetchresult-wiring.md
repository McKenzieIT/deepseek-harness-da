# Agent Note: ui-present-table fetchResult consumer wiring — the result-store primary path

Status: implemented

## Problem

`ui-present-table` resolved a `present_table` `result_id` to its rows via T4's same-turn `query_data` TSV scan (`parseQueryData`). That path is display-truncated (the `renderCompleted` text caps rows + writes an elision marker), fails for any cross-turn reference, and re-RPCs nothing because it reads only the conversation text. [R5](../../../../wayfinder/interpretation-client-rendering/tickets/R5-object-layer-result-cache.md) + [T9](../../../../wayfinder/interpretation-client-rendering/tickets/T9-result-cache-package-impl.md) shipped the object-layer hot cache (`ctx.results`, a session-scoped LRU over the `result.get` RPC) and an inject-face contract; T9's step 6 (the consumer wiring) was deferred because T9's pathspec scoped to `packages/client/result-cache/`. [T10](../../../../wayfinder/interpretation-client-rendering/tickets/T10-consumer-fetchResult-wiring.md) is that deferred wiring: this note records the consumer-side implementation decisions beyond R5/T9's contract.

## Decision

`ui-present-table`'s `apply` adds a `tool.call.toolview` inject face (mirroring `ui-suggest-followups`' `submit` face) that exposes `fetchResult`/`invalidateResult` to `TableCard`. `fetchResult` is the primary row source (a hot-cache `result.get`); the TSV scan stays as the cache-miss fallback (when the result-cache plugin is absent or the host answers `result-not-found`). A `useFetchResult` hook drives the async fetch + the R5 fresh-vs-folded invalidation; `decideTable` resolves the final table data + render state.

- **Inject face over the scoped ctx, degrading gracefully.** `inject = ['slots', 'sessions', 'locale']`; the face does `sessions.scope(sessionId)?.get('results') as TableResultsFace | undefined` (a local mirror of the `ResultService` face) and returns `fetchResult: (rid) => r?.get(rid) ?? Promise.resolve(undefined)` + `invalidateResult: (rid) => { r?.invalidate(rid) }`. The `?? Promise.resolve(undefined)` is load-bearing: a missing service yields a resolved `undefined` (not-found → TSV fallback), never a non-Promise that would throw on `.then`. When the result-cache plugin is absent the whole face is no-op-ish and the card renders the TSV path unchanged.
- **`useFetchResult` is component-internal, subscribes to nothing external.** It holds the inject-face callbacks in refs (`fetchRef`/`invalidateRef`, updated each render) so the effect's identity deps stay `[resultId, freshSeq, retryNonce]` — a new function instance per render (the slot need not memoize the inject face) cannot re-trigger a fetch. The hook uses only `useState`/`useRef`/`useEffect` (no `useSyncExternalStore`, no external subscription) — the AGENTS.md "live data has exactly three channels" rule is satisfied (the async fetch result is local state; the cache is reached through a callback, not a subscription).
- **Fresh-vs-folded via `freshSeq` (the bound query_data's `seq`).** `bindQuery` now retains the candidate's `seq` on `BoundQuery`; `freshSeq` is that seq when the bound query_data's `result_id` matches `args.result_id` (else `null`). The effect invalidates only when `freshSeq` ADVANCES past `lastInvalidatedSeq` (a ref): a new same-turn `query_data` re-ran for this id → invalidate the cache entry → the next fetch misses + re-RPCs fresh (R5). Fold/expand re-renders with the same `freshSeq` → the effect deps are unchanged → no re-run → the cached entry in component state is reused without a re-RPC (G1: fold/expand preserves data). `retry` bumps `retryNonce` → refetch (failures are not cached, so retry re-RPCs).
- **Invalidate-on-first-observation per instance is the v1 safe approximation.** `lastInvalidatedSeq` initializes to `-1`, so a card's first mount with a bound query_data invalidates + fetches. This is intentional: a *new* card instance may observe a `query_data` whose seq is NEWER than whatever a previous instance cached (the cache key is `(sid, rid)`, not seq), so invalidating on first observation is the only way to guarantee the card shows the host's latest rather than a stale snapshot. The cost is a re-RPC when a remount sees the same seq (the cache was already fresh); that is the accepted v1 tradeoff in lieu of R5's deferred generation-token (`qr_R#genN` key rotation), which would let a new `query_data` auto-miss without a manual invalidate. The cache's primary purpose — fold/expand within a card instance does not re-RPC — holds.
- **`decideTable` fallback ladder.** `fetchResult` success → render the entry's full rows (`resultEntryToTableData` coerces `unknown[][]` to the string pipeline the table/KPI/sort/CSV/MD helpers consume; SQL from `entry.metadata?.sql ?? bound.sql`). not-found (undefined) → TSV fallback if a bound `query_data` exists, else "expired" + retry (G1 D2). reject (any error) → "expired" + retry (no TSV fallback on error — the spec scopes the fallback to no-face/not-found, not transport failures). no `fetchResult` face → TSV fallback, no retry (nothing to re-fetch against). `fetchResult` success overrides a TSV "mismatch" (the store is primary; if it has the id, render it).
- **No cross-package import; a local `FetchResultEntry` mirror + duck-typed errors.** `TableCard.tsx`/`index.ts` import nothing from `@deepseek-ai/dsh-client-result-cache` (neither value nor type — AGENTS.md export discipline #3 forbids cross-package symbol imports; the sanctioned routes are the slot system + ctx services, and `ctx.results` is reached through the scoped ctx). `FetchResultEntry` mirrors the wire shape locally (structurally identical, same stance T9 took for its own `ResultEntry` mirror); `TableResultsFace` mirrors the `ResultService` face for the `as` cast (mirroring result-cache's own `ctx.get('connection') as ConnectionHandle`). Errors are duck-typed — the UI treats every `fetchResult` rejection uniformly (expired+retry), so there is no `instanceof ResultFetchError` + no value import; G1 D2 does not distinguish transport from host failure (both are "result store unavailable").
- **`toTableData` is shared by the entry + TSV paths.** The `args.columns` override + the `MAX_DISPLAY_ROWS` cap live in one helper exercised by the TSV tests, so the entry path inherits the same coverage without duplicating the branches.
- **doc-sync: README restructured + `SENTENCE_MODEL_EXPERIENCE` allowlist.** The README's bullet-list "Model Experience" was non-canonical (the gate requires either structured model-context entries or the short "None, as …" form, plus a `#### KV Cache effect` field). The bullet list moved to `## Rendering`; `## Model Experience` is now the short "None, as …" form (ui-present-table is a renderer — it registers no prompt/tool/schema, rendered rows never enter model context) + `## Known Limitations and Deferred Work` (final two H2s, in order). `ui-present-table` was added to the `SENTENCE_MODEL_EXPERIENCE` 'none' allowlist in `scripts/verify-package-readme-model-experience.ts` (mirrors T9 adding `result-cache`).

## Alternatives considered

### Why not import `ResultEntry`/`ResultFetchError` from `@deepseek-ai/dsh-client-result-cache/client`?

AGENTS.md export discipline #3: cross-package imports of another plugin's symbols are forbidden; the sanctioned routes are the slot system + ctx services. A type-only import would erase (no module-graph edge) but still a peer+dev dependency declaration for a value (`fetchResult`) reached through a ctx service — the local `FetchResultEntry` mirror + `TableResultsFace` cast avoid the dependency entirely, the same stance T9 took for its `ResultEntry` mirror of the apiproxy contract. Structural identity makes the cache's `ResultEntry` assignable to the local mirror without coercion.

### Why not `instanceof ResultFetchError` to distinguish transport from host failure?

T12 value-exported `ResultFetchError` for consumers to `instanceof`-narrow. The card does not need to: G1 D2 treats any result-store unavailability (transport or host) as "expired + retry". Duck-typing (treat every rejection uniformly) avoids the value import + keeps the card simpler; the retry re-fetches regardless (failures are not cached).

### Why not skip the first-mount invalidate (init `lastInvalidatedSeq` to `freshSeq`, invalidate only on advance)?

That would preserve the cache across remounts (a remount with the same seq hits instead of re-RPCs). But it is incorrect: a new card instance can observe a `query_data` whose seq is NEWER than the cache's contents (the cache key is `(sid, rid)`, not seq; a previous instance fetched seq-5, the new instance sees seq-8). Skipping the first-mount invalidate would hit the stale seq-5 snapshot + render old rows. Invalidating on first observation is the only correctness-safe v1 choice without the generation-token. The re-RPC on a same-seq remount is the accepted cost (the gen-token, deferred per R5, would close it).

### Why not a cache-internal `query_data` subscription for invalidation?

R5 ruled this out (the runtime `Session` owns the conversation event stream; an external package cannot subscribe without runtime modification, which R5 forbade). The consumer already observes `query_data` nodes through the toolview slot props, so `invalidateResult` is the consumer's call — exactly where T10 puts it.
